# Harness 工作语义覆盖与多会话表现：核对与提案

状态：用户已授权开始实施。事实适配、多会话关注与第一轮表现增强已在第四阶段本地预览实现；默认产品尚未装配该二维工作故事。现行行为以[双线契约](life-work-contract.md)为准，实际验证与边界见[本轮报告](../reports/stage-4-semantics-20261020.md)。

## 已实施的语义与表现

- `WorkFacts` 分开保存驱动、活动、目标、审批／问题、在途工具、结果身份和短反馈。正文／推理／参数不跨入身体事实。
- `WorkSources` 负责附着代次与静默恢复，旧来源回调失效；stream revision 按**每帧递增**处理，并校验 attemptId／index。这是正式 loader 测试发现并纠正的顺序问题，首轮类型核对本身不能代替运行验证。
- goal active 不永久驻岗；审批按原生 id 与四种 outcome 结算；timed 投影不会清掉独立阻塞问题；单个调用失败不变成整个任务失败。
- 多会话共享一个岗位，同级稳定关注、结算后按接纳先后选取。交互会话／草稿独立；后台完成不覆盖审批，输入占用冻结身体并消费短反馈，解除后不补播。
- 思考、输出、模型等待、工具参数、调用等待、许可／答复、恢复／取消／完成有不同表情与空闲姿态；低频视线与原地站坐沿用唯一 tick。减少动态有明确降级。
- 页面有三个可操作组合故事；正式四版本 loader 的事实适配验证与页面模拟分别结算。产品原有正文／未读／可靠提醒不由制作页面重写。

当前仓库实际安装的 agent、session、llm、goal、user-approval、user-questions、tools 均为 `0.2.0-rc.2`。本次核对其公开类型、审批服务实现，以及本地 Host／模型／提醒／第四阶段适配代码。文件摘要见[来源清单](harness-work-semantics.sources.json)。这些资料证明事件接口和代码处理边界，不证明第四阶段已接通真实宿主。

package.json 与 CI 列出 `0.2.0-rc.2`、`0.2.1-alpha.1`、`0.2.1-rc.1`、`0.2.1-rc.2` 四个宿主版本。本次未启动隔离 Harness，后三者没有在本次重新核对；新增事实适配须通过四版本正式 loader 的兼容验证，不能沿用旧完成分类的验证替代新表现通道验证。

结论：Harness 已提供支撑主要工作语义的正式来源；第四阶段适配只接纳其中一部分，当前按钮集合不能视为 Harness 事件全集。先补事实覆盖，再确定注意策略，最后实现表现。

## 事件到语义的对应

| Harness 正式来源 | 能确认的工作语义 | 不能据此推断 | 第四阶段当前覆盖 |
|---|---|---|---|
| 聊天 `accepted`；inbox 准入记录 | 消息已进入指定会话队列 | Agent 已开始执行、请求已答复或任务完成 | 接受回执不算完成，已有；队列活动未投影 |
| `agent/status: running / idle` | 当前 Agent 驱动有／无活动，包括步骤前处理与收尾 | running 不等于正在推理；idle 不等于目标完成 | 现有 Host 有订阅，第四阶段 WorkFacts 未消费 |
| `turn/start`、`step/start/end` | 回合／步骤的进入与退出 | 每个步骤都有可见输出；开始即为模型推理；步骤结束即任务成功 | 仅有回合开始／结束，缺步骤活动 |
| `agent/assistant-stream` 的 `start/chunk/end`，按 attemptId／revision／index 隔离 | 一次模型尝试正在请求／输出／结算 | stream end 或 committed assistant/message 不等于整个回合／目标结束 | PetModel 已处理部分流，第四阶段未消费 |
| chunk `reasoning-delta` / `text-delta` / `tool-call-delta` | 出现推理片段／文本输出／工具参数生成 | 无推理片段不等于没有思考；参数生成不等于工具执行 | 第四阶段统一为 working；应仅提取类别与活动，不传推理正文给角色 |
| `tool/call` ↔ `tool/result`，callId 配对 | 工具调用提出、调用结果已结算；可保留多个在途调用 | call 不保证已进入实际工具体；单个工具成功／失败不证明整个目标成功／失败 | PetModel 有普通工具集合，WorkFacts 无工具活动维度 |
| `tools/execute`／`tools/result` 运行时接口（可选能力） | 工具调度管线进入及规范化结果；具体工具体／外部进程进度仍需对应证据 | 管线进入不代表外部命令已启动或某文件已写成 | 未接；如需要“已执行”语义，须用不改变原 answerer／dispatch 结果的旁观适配并实测 |
| `tool/ptc-dispatch-start` ↔ `tool/ptc-dispatch`，subCallId 配对 | run_code 内嵌套调用的管线进入／结算；保留 root／parent 关联 | 外层 run_code 名称不能代表所有子调用；子调用完成不等于父目标完成 | Broker 用部分结算事件定位问题来源，第四阶段缺开始／结束覆盖 |
| `agent/request-error`、失败／abandoned attempt 与后续正式恢复决定或新 attempt | 请求遇到失败；接纳重试或新尝试后才能表现恢复／重试 | 收到一次 request-error 不等于终止失败，也不保证一定重试 | 第四阶段未区分可恢复失败与终止异常 |
| `approval/asked` ↔ `approval/decided`，原生 id 配对 | 某次审批等待／结算；outcome 为 allowed-once、rejected、cancelled、unavailable | 拒绝不等于 Agent 失败；批准不等于操作成功；结算不等于任务完成 | 待处理集合已有；丢失 outcome，不能设计四类结果反应 |
| `user-questions/request` 运行时 + `userQuestions.active/settled` 正式投影 | 问题 open、continued、已结算；请求信号结束与正式投影共同解释 | 关面板／发送接受／回合结束不证明答复；有问题不证明整个 Agent 停工 | 适配方法仅保留 pending 布尔值，未接真实投影，丢失 open／continued 区别 |
| 问题声明的 `intent.kind: plan-review`（如存在） | 这是方案审阅型问题 | 不能靠问题正文猜出审批或方案状态 | 第四阶段未保留声明的 intent；普通问题与工具权限审批必须分开 |
| `turn/end: completed` + 共享 CompletionTracker | 普通回复／目标仍 active／严格接纳的新目标完成分别分类；合法回合外 goal/change 也由共享判断处理 | completed 回合不等于目标完成；goal-progress 不证明进度百分比或实际前进量 | 已复用分类；还需要把“结果类别”与“驱动是否运行”分开 |
| `goal/change` 及严格公开 goal 投影 | 当前目标身份、active／paused／blocked／complete；已接纳轮次 | goal active 不证明当前 Agent 正在运行；工具参数／台词不证明目标变更 | 分类已接；workDemand 将 goal-progress 持续视为身体占用，后续需修订 |
| `turn/end: error / blocked / max-tokens / aborted` | 终止错误、受阻、输出 token 上限、取消分别处理 | max-tokens 不等于账户额度用尽；用户取消不宜表现成失败或责怪用户 | 主要类别已有；取消 cause 等细节未保留 |
| 恢复历史的 `interrupted`、fork seed 的 `forked`；agent/session 释放 | 历史修复／分叉基线；驱动或会话当前不可观测／已分离 | forked 不是实时异常；Agent 释放不证明持久会话删除或目标成功 | WorkFacts 把未识别终态兜底成 interrupted，包含 forked；真实 epoch／恢复基线尚未装配 |

这些是产品工作表现需要的语义来源，不要求把消息正文、工具参数、系统提示或全部低层日志变成角色动作。事件的 committed 表示会话日志已接纳；是否落盘／checkpoint 是另一边界。

## 当前预览需要先补的缺口

1. **恢复信息维度。** `src/work-facts.ts` 只保留 running、category、requests、needsAttention。需要加入驱动状态、模型／工具活动、请求具体状态、结果身份与 live／baseline 来源；现有 PetModel／Broker 中已具备的事实应复用，避免另造相互冲突的完成分类。
2. **校正模拟输入。** `stage4-preview.js` 的 approval/decided 目前使用 `decision:'allow'`，正式字段是 `outcome:'allowed-once'` 等；approval/asked 正式负载没有 turn。模拟请求重复使用固定 id，不能证明多条独立请求并发。应改为正式类型约束、每次请求唯一身份和完整结果枚举。当前流程测试通过，不表示模拟负载已通过正式服务校验。
3. **补嵌套工具与运行时活动。** 单个工具失败仅改变该调用的事实；在途调用用集合管理。不能收到其中一个结果就清掉其他调用。模型流按 epoch／attempt／revision／index 处理，重连不补播旧表情。
4. **校正结果文案与目标／驻岗关系。** 预览的 max-tokens 文案“预算耗尽”应收窄为输出 token 上限，避免暗示账户额度或目标预算已耗尽。 现有 `goal-progress` 会持续占用工作身体；提案改为按实际驱动、有效未决请求和未确认关注决定驻岗。目标未完成的信息独立保留，Agent 已 idle 且无待处理事项时可以重评生活。
5. **补结构与恢复分支。** forked 静默作为历史基线，interrupted 按恢复来源解释；未知扩展结局保守显示未知，不推断成功或终止错误。断线／分离后保留会话、请求和未读入口，重连重新核对 live 状态。

## 每个会话分别保留的事实：提案

同一会话可以同时“工具运行、有问题待答、目标 active”，这些不应压成一个互斥 mood。

| 维度 | 建议内容 |
|---|---|
| 来源与顺序 | 完整 sessionId、附着代次、正式 seq；模型流另存 attemptId／revision／index |
| 驱动与活动 | idle／running／unknown；准备、模型请求、推理片段、文本输出、在途工具、恢复尝试及活动可信度 |
| 目标 | 无目标／未知／active／paused／blocked／complete，完整目标身份与已接纳轮次 |
| 请求 | 每个审批／问题的原生身份、kind、open／continued 等状态、声明的 intent 和正式结算 outcome |
| 结果与关注 | 回复／目标仍进行／新完成／异常／取消等，结果身份、是否实时新事实、是否已读／已确认 |

活动描述只使用公开元数据；现有正文阅读功能保持独立。没有明确进度事件的工具，可呈现“等待调用结果”的状态及低频动作，不能凭时间编造执行百分比、文件变化或外部成功。

## 多会话表现与协调：待评审提案

### 会话事实、交互焦点、身体关注分别保留

- 所有普通会话独立更新事实与可靠提醒。子代理继续由现有 origin 过滤；未明确建立父子聚合规则前，不把每个子代理当作独立主任务播报。
- 用户正在阅读／输入的会话由显式操作决定。后台事件不改正文、草稿、输入焦点或在途消息的目标身份。
- 身体一次保留一个主要关注会话；同一岗位代表整个工作集合。切换关注主要通过视线、姿态与来源标记表达，不在同一岗位为每个会话重复走一遍。
- 后台会话用稳定来源标识、运行数量、待处理请求数量和新结果提示表达。请求数与会话数分别计数，不用一个总数暗示互斥状态。

### 身体关注选择与节奏

以下优先级属于本产品设计，不是 Harness 声明的事件优先级：

1. 拖动、生命周期、休息、阅读／草稿／发送、输入 active／unknown 等既有占用优先。提醒与后台状态照常按既有权限处理，自动身体动作安静降级；占用解除后重新判断，不补播积压动作。
2. 有可用身体通道时，待用户处理的审批／问题优先，其次未确认的终止异常，再次当前运行的工作。审批和问题默认同级，保留请求是否 continued 的标记，不假设它阻塞所有并行工作。
3. 同级保持当前关注；其结算后取仍有效、等待最久的候选，顺序由本地接纳次序稳定决定。用户显式进入处理的请求优先保持到处理结束。普通流式更新不触发关注切换。
4. 新回复／进展／完成是有身份的短暂反馈，不自动取得长期身体拥有权。后台完成保留其来源和未读；有审批／异常需要关注时只给克制的结果提示，避免整个角色切成“所有工作都结束”的庆祝。
5. 全部驱动已 idle、没有有效待处理请求／未确认关注，才核对生活目标并返回。active 目标保留状态标记，不凭该字段永久坐在岗位。
6. 表情／视线／位移／手部接触仍由唯一协调入口仲裁。提醒及时呈现；身体可以先安全交接物件。安静模式、减少动态及缺动作能力分别降级，不添加第二个调度器。

### 三个组合故事

| 同时发生的事实 | 建议用户能看到的表现 |
|---|---|
| A 正在工具调用，B 请求审批，C 确认真正完成 | 身体主要关注 B，清楚显示 B 在等审批；A 保留运行提示，C 有一次完成结果标记，不夺走审批注意力。用户正在 A 输入时先保留输入与正文，用后台提示告知 B／C |
| A、B 都在持续生成文本 | 稳定关注一个来源，另一个保持运行提示；头部／表情不随两条 delta 流来回切换。两个会话的回复和结果各自保存 |
| A 回合结束但目标 active，B 有 continued 问题，C 已 idle | B 的问题入口仍保留；不能宣布全局完成。B 正式结算且没有运行／未决关注后，即使 A 目标仍 active，也可以重新评估生活目标 |

## 事件语义确认后的表现方向：候选

持续状态定义进入、维持和退出，短事件定义一次反馈；不让每个 chunk 都重启动作。准备／模型等待以收心和有限观察表现；有推理片段时呈现思考姿态；文本输出使用已有组织回复／嘴部节奏；工具在途以专注和等待结果表现；审批偏向征求许可，问题偏向邀请回应；重试适度关切后重新关注；取消温和收住；真正完成才放松并有界庆祝。守候中的站坐转换和小动作受当前主要关注、输入与身体安全限制。

具体姿态、幅度、频率和时间尚未标定；这些候选不能作为已实现的情绪区别。人格／有限记忆仍留在第五阶段。

## 下一步实施与验收门槛

1. 先确认本页语义和多会话策略，修正正式类型夹具与基线／实时分界，补完整事实投影。四个支持版本逐一通过正式 Host loader 的受控事件验证；不依赖真实模型也能复现正常／错误／审批／问题／取消与恢复序列。服务缺失或版本能力不同要有明确降级。
2. 在同一地图把上述三个组合故事做成可操作场景；用相同事实序列验证源身份、旧事件隔离、稳定关注、请求独立结算、用户焦点和返回生活条件。覆盖多工具／嵌套工具、审批四结果、continued 问题、stream abandoned／重试、fork／恢复、断线、容量边界与重复完成。
3. 通过事实／协调检查后实现情绪和动作节奏，测试持续状态不被高频 delta 重启，未决关注不被其他会话庆祝覆盖。继续跑完整 test:inbox-ui 和导航／接触回归，浏览器、隔离原生与用户生活感验收分别结算。
