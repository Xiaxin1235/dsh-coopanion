# 角色提醒与系统通知执行计划

更新：2026-10-12。状态：N0 进行中。接口见 [N0 共享契约](notification-contract.md)，检查结果见 [N0 验证记录](notification-n0.md)。

本阶段交付一套由 Harness 事件驱动的提醒：角色显示时通过动作、表情、互动气泡和待处理信封呈现；角色隐藏时，通过 DSH 界面发送系统通知。实施基线为插件 v0.4.4，支持 DSH 0.2.0-rc.2 和 0.2.1-alpha.1。

本文记录本阶段目标、接口、执行顺序和验收条件。已交付功能继续由 [README](../README.md) 说明，角色接口由 [角色对接文档](characters.md) 说明，发版按 [发布说明](releasing.md) 执行；实施完成后将实际行为同步到这些文档及 [版本记录](release-notes.md)。

## 交付目标

1. Harness 正常启动；桌宠的环境检查、启动、失败恢复与资源释放独立完成。
2. 每次提醒按角色的实际显示状态选择一个呈现通道。
3. 系统通知使用 DSH Desktop 的应用身份，支持权限引导、测试送达及点击返回源会话。
4. 完成、审批、AI 提问、出错、停止、中断和输出上限均有明确的角色行为。
5. 审批与 AI 提问持续未处理时补提醒，支持稍后提醒和多请求合并。
6. 自动化检查、实际安装检查和系统实机验收分别形成可核对的记录。

## 运行与投递

### 宿主与桌宠生命周期

使用 DSH 的 bundle、公开事件、配置和 Connection 接口挂载插件。可选能力通过 `ctx.inject` 接入；监听、计时器、请求及进程资源由对应 context 的 effect 持有和释放。

插件完成注册后异步启动桌宠。环境探测、Electron 准备及窗口握手在桌宠启动任务内完成；启动期间 Harness 保持可用。缺少桌面会话、运行时缺失、启动超时、子进程退出与清理失败均转换为桌宠状态及有界诊断，设置页提供重试入口。停止与卸载可取消启动任务并等待有界清理。

安装兼容性按声明的 DSH 版本和包依赖检查；运行能力按实际桌面环境检查。本阶段验证 Desktop、本机 `dsh web` 及 CLI 的启动行为，无桌面环境验证 Harness 启动和插件状态反馈。

| 桌宠状态 | 投递行为 |
|---|---|
| 运行且角色显示 | 角色呈现；任务状态、最终回复和待处理内容同步更新 |
| 运行且角色隐藏，系统通知开启 | 由已连接的 DSH 客户端领取提醒并发送系统通知 |
| 运行且角色隐藏，系统通知关闭、权限受限或客户端暂不可用 | 保存待处理状态，角色重新显示时提供入口 |
| 启动中 | 保存状态，窗口就绪后按当前状态呈现 |
| 已退出或启动失败 | 保存会话派生状态；重新启动后展示当前结果与待处理项 |

角色显示状态使用原生窗口的 show / hide 回执，并携带运行代次和显示状态版本。每次初次提醒或补提醒只产生一次通道领取；显示切换后再次核对状态。锁屏与屏幕休眠期间保留待处理内容，恢复后重新检查请求是否仍待处理及当前投递条件。

桌宠停止时关闭投递资格并撤销计时器、在途领取和等待投递的提醒。新进程使用新的运行代次。角色重新显示或桌宠重新启动时从状态恢复待处理入口及未读结果。

### 系统通知与权限

Host 识别事件并安排投递；Client 在 DSH 自己的应用界面内调用标准 Web Notifications API。DSH Desktop 由其 Electron 应用承载通知，本机 `dsh web` 则由访问页面的浏览器承载通知。

在 **Settings → 桌宠** 增加独立的系统通知开关、权限说明、测试通知及系统设置引导。用户开启后执行权限申请流程，测试按钮返回本次测试的真实状态。

权限与投递分别记录：网页权限为未申请、允许、拒绝或不可用；系统授权为已确认、受限或待确认；投递为已领取、已请求、收到显示回执、失败或结果待确认。系统设置变化、专注模式、客户端重载和重连后刷新可取得的状态，并保留测试入口。

macOS 首先使用实际签名的 DSH Desktop 验证应用名称、通知权限和通知中心留存。点击通知时，通过公开会话操作定位完整 `sessionId` 并唤回 DSH。已查看结果与待回答／待审批请求分别确认。

Client 用 Host 颁发的领取结果投递，回执关联提醒 id、客户端 id 和运行代次；同一提醒可由一个客户端领取。领取过期或客户端失联后，根据最后已确认的步骤区分待投递与结果待确认，保留可核对的投递状态。通知中心中的已送达通知按系统策略留存，运行中的点击处理映射到源会话。

### 配置

现有 `notifications` 保留为任务提醒开关，角色状态、最终回复和未读结果继续按会话更新。新增配置经 Harness 设置持久化，桌宠菜单、托盘与设置页显示一致状态。

| 配置 | 默认值 | 行为 |
|---|---|---|
| `notifications` | `true` | 开启事件触发的角色提醒及任务通知投递 |
| `systemNotifications` | `false` | 用户开启并完成权限引导后，角色隐藏时允许系统通知 |
| `reminders` | `true` | 为仍待处理的审批／提问安排自动补提醒 |
| `reminderDelayMs` | `600000` | 初次提醒后等待时长，可设为 1 分钟至 24 小时 |

旧配置保留 `notifications` 的已保存值，新增字段使用默认值。关闭任务提醒时取消主动投递及补提醒调度，保留请求和阅读状态；重新开启时从仍有效的请求安排后续提醒。配置迁移、启用、关闭、恢复及非法值处理纳入验证。

## 事件与角色互动

会话身份、回合、事件序号及请求状态从 Harness 公开接口和已提交事件取得。审批使用 `approval/asked`、`approval/decided` 的请求 id 配对；AI 提问在两版宿主中核对公开提问接口及持久记录，并绑定具体请求／工具调用及处理结果。恢复时折叠历史得到当前待处理状态，实时尾部事件产生新提醒。

| 事件 | 角色行为 | 内容与操作 |
|---|---|---|
| 思考、生成、工具工作 | 思考／专注表情，生成时嘴部变化 | 更新进行中的状态 |
| 完成 | 开心表情，约 2.5 秒后待机 | 关注会话最终回复进入阅读气泡；后台结果进入未读列表 |
| 等待审批 | 停止闲时活动，担忧／等待表情 | 短提示“下一步需要你确认”，点击回到源会话处理 |
| AI 提问 | 注视用户，轻微歪头或角色支持的提问动作 | 短提示“有个问题想问你”，提供问题预览及源会话入口 |
| 回合出错 | 难过表情，信封标记待查看 | 提示查看会话详情 |
| 用户主动停止（`aborted`） | 短暂停顿或点头，然后待机 | 提示“先停在这里，随时继续” |
| 恢复发现未完成回合（`interrupted`） | 困惑／担忧，进入待处理列表 | 提示“这段任务中断了，陪你回去看看” |
| 被阻塞、达到输出上限 | 等待表情 | 提示“任务暂时停下了，看看下一步怎么继续” |

恢复发现的中断使用当前恢复状态呈现；各类停止原因按宿主的实际语义分类。工具单步错误保持“正在处理”的状态，回合结算决定最终提醒。

互动提示与最终回复阅读分别管理。关注会话保持用户选择；新事件更新待处理入口，当前输入、阅读、拖拽或动作完成后再呈现排队的互动。提示提供键盘操作并遵循减少动态效果及音效设置。角色动作按词表调用，缺少动作时回退到可用表情和信封。

### 超时补提醒

每个审批／提问请求拥有独立计时和处理状态，默认 10 分钟后自动补提醒一次。角色显示时轻轻挥手、注视用户，并提示“刚才那件事，还等你看看”；角色隐藏时按系统通知配置投递。多个请求同时到期时合并成一次互动，展示数量及待处理列表入口。

请求已回答、审批已决定、取消或会话销毁时撤销计时。限时提问在回合结束后仍可能保持 continued，补提醒按公开提问投影中的有效请求安排；阻塞请求按其运行中答复／取消信号结算。打开通知和会话记录查看动作；请求是否结算以 Harness 的处理结果为准。“稍后提醒”重新安排该请求的到期时间；显示提醒、隐藏角色和切换会话保留请求状态。处理结果与到期任务并发时，投递前再次检查请求有效性。

## 实施接口与文件归属

首个检查点确定共享类型与消息协议，随后两条实现线消费同一接口。类型放在独立模块，Host、DSH Client 与桌宠都引用它。

| 对象／操作 | 必需信息与语义 |
|---|---|
| 事件提醒 | 稳定 id、完整 sessionId、回合、源事件序号、类别、时间、初次／补提醒阶段、可选请求 id／callId |
| 待处理请求 | 请求 id、会话、类型、预览、有效／已结算状态、到期时间、自动补提醒次数、稍后提醒时间 |
| 桌宠运行状态 | 阶段、运行代次、原生可见性及版本、可用性、失败原因 |
| 通道领取与回执 | 提醒 id、客户端 id、运行代次、领取期限、通道、投递状态及有界失败原因 |
| 用户动作 | 打开源会话、确认具体回复已读、稍后提醒；动作携带对应会话／结果／请求 id |

Host 持有事件去重、请求结算、计时与通道选择；Client 持有网页权限、系统通知对象、领取与投递回执；桌宠持有角色动作与气泡呈现。生命周期取消、迟到回执及会话销毁在接口中具有明确结果。

## 执行顺序

整个通知改造作为一个阶段推进，按下面的检查点交付。

| 检查点 | 工作与产物 | 完成条件 | 当前状态 |
|---|---|---|---|
| N0：通知路径与共享接口 | 使用工作区中的最小插件，经 DSH 正式插件机制安装到隔离测试 profile；验证实际 Desktop 的通知身份、权限、通知中心及会话点击；核对两版提问／审批接口；确定消息协议、状态转换、配置迁移和文件归属 | 远端 CI 通过，单实例通知身份／留存／点击通过，共享接口与产物记录绑定同一共同基线 | 进行中 |
| N1：Host 实现（A） | 异步启动及失败恢复；事件分类与请求配对；通道选择、领取、去重、计时和补提醒；公开 Connection 路由 | Host 测试覆盖事件生命周期、并发和失败；提供消费接口及检查结果 | 等待 N0 |
| N2：界面实现（B） | DSH Client 系统通知、配置和权限引导；角色行为、互动提示、稍后提醒、未读入口及双语文案 | 客户端与角色测试覆盖交互、回执、动作回退和可访问性；接口与 N0 一致 | 等待 N0，可与 N1 并行 |
| N3：集成验证 | 合并 A／B；接入共享入口和原生窗口消息；三平台及两版宿主安装测试；签名 Desktop 通知实机验收 | 计划内自动检查与实机验收通过，用户验收结论已记录；问题修复后按同一产物复核 | 等待 N1、N2 |
| N4：交付 | 同步使用说明、角色映射、版本记录；提交版本更新，按现有发布流程交付已验证压缩包 | 文档与实际行为一致，验收记录绑定最终源码和分发产物 | 等待 N3 |

N0 的首个实际验证点为 macOS DSH 身份、通知中心留存及点击会话。检查结果同时记录可取得的授权状态和投递回执；需要补充的公开宿主能力明确列入 N0 后续工作，完成后再确定 N1／N2 的相关接口。

N0 保持现有插件与锁文件版本，通过 PR 的 CI 运行生成验证 artifact。N0 完成后自动从通过检查的同一提交创建 N1／N2 worktree 并开始并行开发。

## 多 worktree 推进

采用“串行确定接口 → 两个 worktree 并行实现 → 串行集成”的安排。N0 由集成负责人完成，形成已提交的共同基线；N1／N2 从同一提交创建分支和 worktree。

| 分支建议 | 负责文件与工作 | 交接内容 |
|---|---|---|
| `codex/notification-host`（A） | `src/model.ts`、`src/controls.ts`、新增 Host 提醒／调度模块、`tests/model.test.ts`、`tests/controls.test.ts` 及新增 Host 测试 | Host 实现提交、实际检查结果、接口使用说明 |
| `codex/notification-ui`（B） | `src/client/Settings.tsx`、`src/client/locales.ts`、客户端样式、新增 Client 通知模块；`web/pet.js`、`web/session-ui.js`、`web/index.html`、`web/style.css`；`tests/ui.mjs`、`tests/presentation.test.js` 及新增 Client 测试 | Client／角色实现提交、实际检查结果、截图及回执用例 |
| `codex/notification-integration`（集成） | 共享类型、`src/index.ts`、`src/bridge.ts`、`src/client/index.ts`、`desktop/*`、包清单／锁文件、构建与 CI；`tests/plugin.test.ts`、`tests/bridge.test.ts`、`tests/desktop.mjs`、安装测试／fixture 及阶段文档 | 共同基线、整合提交、完整验证产物与验收记录 |

新增模块可在各自 worktree 完成，入口装配由集成负责人统一完成。A／B 使用 N0 的共享契约进行局部验证，完整入口和真实宿主验证在集成分支完成。接口调整先进入共同基线，再同步到两个实现分支。每条分支交接一个可独立审阅的提交序列及验证结果。

各 worktree 使用独立依赖目录、构建目录、临时 profile、端口、角色数据及测试输出；签名应用、系统权限、通知中心和物理桌面的验收在同一机器上串行执行。A 先整合事件与生命周期，B 随后整合呈现，再完成端到端验证；最终报告绑定整合后的同一提交和压缩包。

## 验证与验收

### 自动检查

沿用项目固定工具链及现有 CI，新增用例归入相应的类型、单元、浏览器、桌面及安装检查。

| 范围 | 必测场景 | 证据 |
|---|---|---|
| Harness 启动 | 自动启动开启／关闭；缺少显示环境／运行时；启动超时；启动期间停止；异常退出；清理失败；插件卸载 | Harness 就绪结果、桌宠状态、资源清理记录 |
| 事件语义 | 两版宿主的审批／提问及处理结果；各类回合结束；历史恢复；重复及迟到事件；并行请求；子代理与多个顶层会话 | 实际事件样本、归类与状态测试 |
| 投递路由 | 显示／隐藏切换；旧运行代次消息；多个 Client 竞争；断连、重连、重载、领取过期；退出时在途投递取消 | 通道、领取及回执记录 |
| 补提醒 | 可控时钟；请求到期、稍后提醒、结算与到期并发、多请求合并；会话销毁／插件卸载；锁屏恢复 | 调度测试与取消结果 |
| 角色交互 | 各类别动作、互动气泡、阅读及输入保护、后台会话、小信封、动作缺失回退、减少动态效果、键盘与双语 | 浏览器／原生窗口检查及截图 |
| 配置与客户端 | 旧配置加载、独立开关、权限状态、测试通知成功／失败、点击源会话、网页允许且系统拒绝、客户端不可用 | 配置及客户端检查结果 |
| 分发安装 | Linux／macOS／Windows × DSH 0.2.0-rc.2／0.2.1-alpha.1；消费同一压缩包 | 六组安装报告、包摘要及 CI 链接 |

调度测试使用可控时钟；系统通知适配器的自动检查验证调用、回执和失败处理。具有交互桌面会话的测试机补充实际 OS 投递检查。

### 系统实机验收

macOS 使用实际签名 DSH Desktop；Windows 使用实际安装的 Desktop；Linux 使用声明支持的桌面会话。验收内容包括：

1. 首次启用、允许授权、拒绝授权及随后从系统设置恢复。
2. 角色显示时的角色提醒；隐藏时的系统通知；退出后的投递停止。
3. 系统通知中的应用名称、通知中心／系统通知列表留存、点击定位正确会话。
4. DSH 主窗口隐藏、客户端重载／重连、系统专注设置、锁屏及休眠恢复。
5. 审批／提问的实际处理与超时补提醒，包含多个同时待处理请求。
6. 安装后重启、配置恢复、旧通知点击及对应会话已销毁时的反馈。

使用受控的真实 Harness 事件完成可重复验收，再通过真实模型会话检查实际提问、工具审批和回合结束。人工操作步骤与自动操作各自记录结果。

### 验收记录

N0 保存原型产物摘要与工作区来源；N3／N4 保存源码 commit、插件版本、同一分发包 SHA-256、DSH 版本、Desktop 应用标识与签名、OS 版本、权限和显示状态、事件／请求／提醒 id、投递回执、通知中心及点击证据、检查时间和验收人。

记录按 `pass`、`fail`、`pending`、`unavailable` 标记每项结果。自动检查、OS 送达检查、真实模型会话与用户验收各自结算；修复后更新对应证据，并保留失败记录。每次检查点交接列出已通过项目和仍待完成的验收项，阶段完成结论对应 N3／N4 的完成条件。
